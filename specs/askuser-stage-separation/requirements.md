# AskUser 阶段职责分离需求

## 审批摘要

### 目标

让 LazySpec 在 Brainstorming 和 Design 阶段分别收集需求决定与设计决定，避免把需求方向误作实现方案。

### 范围

- 包含：Brainstorming 的需求问题边界、Design 的独立设计提问、跨阶段决定传递及问答工具适配。
- 不包含：具体产品功能实现、固定某个 Agent 的问答工具或参数格式。

### 核心行为

- Brainstorming 只询问目标、范围、用户可观察结果、约束、风险和成功标准；实现方案由 Design 阶段另行讨论。
- Requirements 获得明确批准后才能进入 Design；新建 Design 前必须单独询问设计决定或补充约束并等待回答，修订时不重复已回答的问题；设计回答不等于文档批准。
- Requirements、Design、Tasks 各自完成后单独审批，上一阶段未获批准前不得生成下一阶段文档；决策影响程度和风险等级不改变这三个审批门，Tasks 批准不自动授权执行。
- 问答工具按当前环境提供的能力调用，不硬编码名称或参数结构。

### 风险与待确认

- 风险等级：medium；理由：跨阶段改变 LazySpec 的用户交互和决策边界。
- 关键操作：无。
- 风险：若两个阶段的问题边界不清，可能过早固定实现选择或重复询问用户。
- 待确认：无。

## 引言

本 Spec 为 LazySpec 的 Brainstorming 与 Design 问答阶段建立清晰边界，并用一个小型示例功能验证两阶段分别向用户收集决策。

## 需求

### 需求 1：Brainstorming 仅收集需求决定

**用户故事：** 作为 LazySpec 使用者，我希望 Brainstorming 只确认需求方向，以便 Requirements 描述用户需要的结果，而不提前锁定实现方式。

#### 验收标准

1. <a id="req-1-1"></a> 当 Brainstorming 询问用户时，系统必须将问题限定在目标、范围、用户可观察行为、约束、风险或成功标准。
2. <a id="req-1-2"></a> 当用户未提出绑定性技术约束时，Brainstorming 必须把架构、接口、数据模型、依赖及恢复策略留给 Design 阶段决定。
3. <a id="req-1-3"></a> 当 Brainstorming 生成会话 Context 时，`selectedApproach` 必须表达需求方向，不得被视为已批准的实现设计。

### 需求 2：Design 独立收集设计决定

**用户故事：** 作为 LazySpec 使用者，我希望在 Design 阶段另行回答设计问题，以便设计文档反映我对实现边界和取舍的决定。

#### 验收标准

1. <a id="req-2-1"></a> 当系统首次创建 Design 时，系统必须在起草前单独询问至少一个设计层面的问题，并等待用户回答。
2. <a id="req-2-2"></a> 当设计选项需要用户选择时，系统必须说明推荐选择及主要取舍，并一次只询问一个决定，不按影响程度改变提问规则。
3. <a id="req-2-3"></a> 当没有待选设计方案时，系统必须邀请用户补充设计约束或偏好，并允许用户明确回答“无”。
4. <a id="req-2-4"></a> 当修改既有 Design 时，系统不得重复询问已明确回答过的问题；新出现且尚未回答的设计选择必须单独询问。
5. <a id="req-2-5"></a> 当当前 Requirements 尚未明确获批时，系统不得开始 Design 阶段的提问或生成 `design.md`。

### 需求 3：阶段决定与审批保持独立

**用户故事：** 作为 LazySpec 使用者，我希望阶段问答不会替代需求或设计审批，以便每份审批对应完整且可审阅的内容。

#### 验收标准

1. <a id="req-3-1"></a> 当 Design 选择会改变已定义的用户可观察行为或范围时，系统必须返回 Requirements 处理该决定后再固定设计。
2. <a id="req-3-2"></a> 当用户回答 Design 问题后，系统必须将该决定用于 Design 草稿，但不得将该回答视为 Design 或完整 Spec 的批准。
3. <a id="req-3-3"></a> 当 Requirements 草稿完成时，系统必须先请求该文档的明确批准；未获批准前不得生成 `design.md`。
4. <a id="req-3-4"></a> 当 Design 草稿完成时，系统必须先请求该文档的明确批准；未获批准前不得生成 `tasks.md`。
5. <a id="req-3-5"></a> 当 Tasks 草稿完成时，系统必须单独请求该文档的明确批准；Tasks 批准不自动授权执行。
6. <a id="req-3-6"></a> 无论风险等级或决策影响程度如何，系统都必须保留 Requirements、Design、Tasks 的顺序与三个独立审批门，不得自动生成三份文档后合并审批。

### 需求 4：问答工具适配当前环境

**用户故事：** 作为使用不同 Agent 环境的用户，我希望 LazySpec 使用当前环境可用的问答工具，以便工作流不依赖某个工具名称或专属参数格式。

#### 验收标准

1. <a id="req-4-1"></a> 当当前环境提供适用且允许使用的问答工具时，系统必须依据该工具实际支持的字段调用，不得要求固定工具名称或照搬其他 Agent 的输入结构。
2. <a id="req-4-2"></a> 当当前环境没有适用的问答工具时，系统必须在会话中直接提问并等待用户回答。

# Spec Writing Prompt

Follow these guidelines when generating `spec.md`. It is LazySpec's only planning artifact: one approved file carries the contract, the task list, and the verification method.

1. **One artifact**: Never create `plan.md`, a verification file, or any other planning artifact. `spec.md` holds behavior, structure, decisions, risks, tasks, and verification.
2. **Structure diagram**: Put exactly one non-empty Mermaid block under `## 结构图`, after `目标与范围` and before `用户故事`. Show the feature boundary, affected components, their material dependencies, the primary flow, and each material failure or recovery path. Use one of `flowchart`, `sequenceDiagram`, `stateDiagram-v2`, `erDiagram`, or `classDiagram`, keep the section within 24 lines, and use conceptual names rather than file inventories, call-site maps, or code. The diagram must not introduce behavior or dependencies absent from the user stories, acceptance criteria, or decisions, and it never replaces a distinct acceptance, decision, risk, or verification item.
3. **User stories**: Give every story a stable `S<n>` ID and exactly one line: `作为…，我希望…，以便…`. Write the story once; the acceptance table references its ID instead of repeating the text.
4. **EARS acceptance criteria**: One table row per criterion. `类型` is the EARS category (普遍, 事件, 状态, 异常, 可选); `当` is the trigger or condition; `系统应` is the observable result. Keep exceptions and failure paths as separate rows; never merge them into a happy path. IDs are `R<story>.<n>` and stay stable across revisions.
5. **Inline verification**: The `验证` column is the approved check for that criterion (command, probe, or named end-to-end check). A shared command may cover several criteria; add one `组合：…` line only for composed flows. State the full test suite command once, on the relevant row or the combination line. Do not add a separate verification table or `Planned Checks` section.
6. **Decisions**: Record only choices that materially affect implementation: architecture, interfaces, data ownership, compatibility, and important tool, library, package, service or custom-implementation choices. One row per decision with a one-line reason. Fill `放弃` only when a rejected alternative matters to review or maintenance; otherwise write `无`. Specify an exact version only when it is material to compatibility or the contract. Do not add an inventory or separate selection report.
7. **Risks**: Record the assessed level with its reason and the critical operations that need explicit authorization. Add invariants only when acceptance criteria do not already express them, and reference `R` IDs instead of repeating text.
8. **Tasks**: One line per task: `- [ ] //TODO <n>. <behavioral action> → R<id>；检查：<basic check>`. Each task is an independently deliverable behavior slice, not a file or layer. Do not copy the scenario or acceptance text; reference the `R` ID. Reserve full test suites and end-to-end execution for the final verification pass.
9. **Execution record**: Keep the four fixed lines (`状态`, `验证`, `结果`, `未决`). While executing, update only `执行记录`; the only permitted change inside the contract sections is the task checkbox `[ ]` → `[x]`. Do not record fingerprints, per-check timestamps, or raw logs.
10. **Single source**: Write each behavior, decision, risk, and check exactly once and refer to IDs elsewhere. Put component relationships, boundaries, and flow only in the structure diagram; do not repeat them as prose. Do not write background, motivation, value narration, implementation steps, file inventories, call-site maps, code, or test code.
11. **Shape and budget**: Keep `目标与范围` to two lines, the structure diagram within 24 lines, at most 12 acceptance rows, 5 decisions, 3 risk rows, 12 tasks, and 5 execution-record lines. When a section exceeds its budget, merge duplicate criteria and delete narration first; if still over, split the feature into separate Specs. Never drop a distinct acceptance behavior to shorten the document.

Use [spec-template.md](spec-template.md) for frontmatter and section shape, and keep lifecycle metadata plus stable `S`/`R` IDs across revisions.
